這個控制台裡沒有任何真正的 VM。沒有 gVisor，沒有 Firecracker，沒有 Agent API， terminal 只認得寥寥幾個模擬指令。把它叫「產品」太沉重——它是一個問題的具體化：**當 Agent 需要一個地方跑工作時，操作者到底需要什麼？**

## 先驗證流程，再驗證基礎設施

沙盒產品最貴的錯誤，不是選錯 runtime，而是花六個月把隔離層做完，才發現使用者真正在意的是別的東西。所以我們把順序倒過來：先用瀏覽器模擬出完整的操作旅程，確認每一段流程都有人要走，再談底層。

這個原型刻意包含了三個我們認為最關鍵的假設：

1. **Agent 需要的是狀態，不是固定的機器。** Active、Idle、Suspend 三段式生命週期，對應「運算中」、「待命」、「保存工作區但不計算」。你可以直接在控制台把狀態切來切去，感受差異。
2. **不活動時不該付全價。** Usage 頁的 auto-tiering policy 可以調整降級門檻，同一小時的工作成本會和 E2B、Daytona、Modal 等競品並排比較。「不為等待 LLM 回覆付全價」是整個產品的核心主張。
3. **檔案跟著沙盒走。** 上傳、下載、快照、分支——工作區的內容必須在暫停與接續之間完整保留，這是「Suspend」有意義的前提。

## 哪些是真的，哪些是假的

為了避免誤導，列清楚：

- **真的**：狀態計時與降級邏輯。重新整理後倒數會接續，關閉頁面期間不計時，背景計時器延遲時會把時間正確分配到各狀態。這部分是認真寫、認真測過的（見 `lifecycle.js` 與它的測試）。
- **假的**：費率（示意值，不是報價）、terminal（只支援 `help`、`ls`、`status` 等少數指令）、檔案傳輸（只進到你自己的瀏覽器，最多 10 MB）、以及 Resume（只切換模擬狀態，背後沒有任何東西被暫停或恢復）。

## 接下來

下一步不是把假的換成真的那麼簡單。真正的隔離層（gVisor / Firecracker）、控制平面 API、計量與帳務，每一層都需要先驗證可行性。我們在 [runner 語言 ADR](https://github.com/our-sandbox-agent/sandbox-console/blob/main/docs/adr/runner-language.md) 已經決定 Runner 與 CLI 用 Go，gVisor 的最小驗證矩陣也在準備中。

這個部落格會記錄每一個技術決策與驗證結果——包括失敗的。歡迎盯著我們做。
